# day1-02Git与项目版本管理

很多新手把Git当成“上传代码到网盘的工具”，这是极大的误解。Git是世界上最先进的分布式版本控制系统，它本质上是一台属于你本地的“代码时光机”

### ▼ 一、先建立核心认知：Git 是代码的“游戏存档”

想象你在玩一款超级复杂的RPG游戏（比如《塞尔达》），你要打最终Boss了：

* 没存档直接打：死了就得从头跑图，心态炸裂。
* 每过一道关卡存一次盘：死了直接读档，从最近的安全点重来。

代码开发就是这款游戏。你每写一个功能、修复一个Bug，都是在前进。Git 的作用就是帮你在本地硬盘上建立无数个“存档点”（Commit）。

| 游戏术语 | Git 术语 | 解释 |
| :--- | :--- | :--- |
| 游戏存档 | 提交 (Commit) | 对当前代码状态的一次“快照”拍照，包含唯一的ID（Hash值）和时间戳 |
| 存档列表 | 提交历史 (Log) | 你所有存档的流水账记录，按时间倒序排列。 |
| 读档/回档 | 恢复/重置 (Reset / Revert) | 把当前代码退回到某一次提交时的状态 |
| 角色当前状态 | 工作区 (Working Directory) | 你现在正在编写、还未存档的代码。 |

> 🔥 **飞书重点**：Git 的绝大多数操作都发生在你的本地电脑上，不需要联网！只有 `push`（推）和 `pull`（拉）时才需要连接远程仓库（如GitHub/GitLab）。

### ▼ 二、本地仓库三大区域（必须牢记的底盘逻辑）

在执行任何Git命令前，请先记住这张终极地盘图。你的代码流转遵循严格的路径：工作区 -> 暂存区 -> 本地仓库。

| 区域名称 | 英文名称 | 通俗比喻 | 对应的操作 |
| :--- | :--- | :--- | :--- |
| 工作区 | Working Directory | 你的草稿纸。你在电脑文件夹里看到的、正在编辑的所有文件。 | `git add` 将草稿誊写到“等候区”。 |
| 暂存区 | Staging Area / Index | 提交前的等候区/缓冲区。准备要存档的文件清单，但还没真正写入历史。 | `git commit` 将等候区的清单正式“封存”成永久存档。 |
| 本地仓库 | Local Repository | 你的永久存档库。所有已经commit的历史版本都安全存放在此（保存在项目根目录的 .git 隐藏文件夹里）。 | `git log` 查看永久存档列表。 |

### ▼ 三、极简核心命令手册（入门必备七招）

以下命令覆盖了日常开发的 90% 场景。请务必对照上述“三大区域”来理解每个命令移动的是哪里的数据。

#### 1. 初始化或克隆（初始化存档库）

* `git init`：在当前文件夹下创建一个新的本地仓库（会出现一个隐藏的 `.git` 文件夹）。千万不要在桌面或系统盘根目录执行此命令！
* `git clone <仓库地址>`：把远程服务器（如GitHub）上的完整存档库（包括所有历史记录）完整复制到你本地电脑。

#### 2. 查看状态（侦察兵）

* `git status`：每天使用频率最高的命令。它会告诉你：当前工作区有哪些文件被修改了？哪些文件被放进了暂存区？哪些文件未被Git追踪？

> 💡 建议每执行一次操作，就敲一次 `git status`，它会像导航仪一样告诉你下一步该干嘛。

#### 3. 提交流程（两步走）

存盘必须分两步走，不能一步到位：

* **第一步（加入等候区）**：`git add <文件名>` （或 `git add .` 添加当前目录所有变更）。
* **第二步（正式封存存档）**：`git commit -m "写清楚这次改了啥"`。

> ⚠️ 提交信息（-m 后面的内容）是写给队友和自己看的。规范的格式如：`fix: 修复了登录按钮点击无响应` 或 `feat: 新增用户积分计算模块`。

#### 4. 查看历史存档（时光机列表）

* `git log`：显示完整的提交记录（作者、日期、Hash ID、提交信息）。
* `git log --oneline --graph --all`：强烈推荐，以简洁的一行摘要加图形分支方式显示，视觉上最美观。

#### 5. 对比差异（找不同）

* `git diff`：查看工作区和暂存区之间的差异（即你现在改了哪些还没 `add` 的内容）。
* `git diff HEAD`：查看工作区和最新一次提交（HEAD）之间的差异。

### 四、“后悔药”指南：历史版本恢复（核心安全知识）

这是Git最强大的功能，也是最容易误操作的地方。恢复代码只有两种核心逻辑：

| 命令 | 适用场景 | 本质效果 | 风险等级 |
| :--- | :--- | :--- | :--- |
| `git reset --hard <版本号>` | 本地代码改烂了，想彻底丢弃最近的所有改动，强行跳到某个旧存档。 | 移动当前分支的指针，并强制覆盖工作区和暂存区。 | 🔴 **高危**：会永久丢失未提交的本地修改！ |
| `git reset --soft <版本号>` | 想把最近几次的提交“撤回”到暂存区，重新整理后再提交。 | 移动指针，但保留工作区和暂存区的改动。 | 🟡 **中危**（需谨慎操作） |
| `git revert <版本号>` | 想“安全地撤销”某个历史版本，尤其是在多人协作时。 | 不删除历史，而是新增一个“反向提交”来抵消那次变更的影响。 | 🟢 **最安全**（多人协作首选） |

> 🔥 **黄金法则：**
> 
> 1. 如果代码已经 `push` 到了远程仓库（GitHub/GitLab），永远不要用 `reset`，请用 `revert`。因为 `reset` 会改写历史，导致队友的本地代码与远程冲突崩盘。
> 2. 如果你不确定自己改了什么，执行 `git reset --hard` 之前，务必先 `git stash`（暂存当前修改）或备份整个文件夹！

#### 实战场景：我刚提交完发现提错了，想撤回最近一次提交，但保留代码改动？

* **解法**：`git reset --soft HEAD~1`
* **解释**：`HEAD~1` 表示“上一个版本”。执行后，最近一次的提交被撤回，但你的代码改动还安安稳稳地躺在暂存区里，你可以重新 `add` 和 `commit`。

### 五、忽略文件 (.gitignore)：别把“垃圾”存进仓库

有些文件（如编译产生的 `.class` 文件、Python的 `pycache`、本地的配置文件 `.env`、大体积的日志文件）绝对不应该被提交进Git仓库。

在项目根目录创建一个名为 `.gitignore` 的文本文件，在里面逐行列出要忽略的规则。

典型内容示例（Python项目）：
```text
# 编译产物
__pycache__/
*.pyc
# 虚拟环境
venv/
.venv/
# 环境变量（包含密码，绝不能上传）
.env
# IDE配置文件（每个人的喜好不同）
.vscode/
.idea/
```

> 💡 **操作习惯**：在 `git add` 之前，先写好 `.gitignore`。如果某个文件已经被 `add` 进去了，再写 `.gitignore` 是无效的，需要用 `git rm --cached <文件>` 将其先从暂存区移除。

### ▼ 六、建立正确的“版本意识”（软技能）

有了工具，更要有意识。请把下面三条刻在脑子里：

1. **原子化提交**：一个提交只做一件事。不要攒了一周的代码一次性提交。比如“修复登录Bug”提交一次，“增加导出Excel功能”再提交一次。这样回滚时，你只会丢掉“导出Excel”的代码，而不会牵连“登录修复”。
2. **提交信息即文档**：队友（包括未来的你）看 `git log` 的时间比看代码注释的时间还长。请用规范的动词开头：`feat:`（新功能）、`fix:`（修复）、`docs:`（文档）、`refactor:`（重构）。
3. **每天上班第一件事**：`git pull`；每天下班前最后一件事：`git push`。永远保证本地仓库不落后于远程，避免“冲突地狱”。

### ▼ 七、终极速查表（贴在工位旁）

| 你想要做什么 | 请输入的命令 |
| :--- | :--- |
| 我要初始化一个新项目 | `git init` |
| 我要把远程代码下载到本地 | `git clone <url>` |
| 我改了代码，想看看改了哪些文件 | `git status` |
| 我想把改的内容加入暂存区（准备提交） | `git add .` |
| 我想把暂存区正式存盘 | `git commit -m "说明文字"` |
| 我想一次性完成 add + commit（仅针对已追踪文件） | `git commit -am "说明文字"` |
| 我想看提交的历史记录 | `git log --oneline --graph` |
| 我刚才改乱了，想彻底回到上一次提交的状态（丢弃改动） | `git checkout .`（丢弃工作区）或 `git reset --hard HEAD`（重置所有） |
| 我提交错了，想撤销这次提交（保留代码） | `git reset --soft HEAD~1` |
| 我想把本地的存档同步到GitHub | `git push` |
| 我想把队友的最新代码拉到本地 | `git pull`（相当于 fetch + merge） |

### 写在最后

Git 不是“上传工具”，而是你本地开发环境的安全网。有了这张网，你就敢于在代码里大刀阔斧地重构和实验，因为你知道，无论改得多烂，一个 `git reset` 就能回到昨天那个能跑的版本。

一个程序员的专业度，是从写好 `.gitignore`、写好 `commit message`、以及用好 `git status` 开始的。请务必在你电脑上新建一个测试文件夹，把上面的命令逐个敲一遍，把输出结果看清楚。肌肉记忆比死记硬背更重要。
